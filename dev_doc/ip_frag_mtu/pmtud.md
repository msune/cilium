# Path MTU Discovery (PMTUD)

Path MTU Discovery (PMTUD) is described in [RFC1191](https://datatracker.ietf.org/doc/html/rfc1191)
for IPv4 and in [RFC1981](https://datatracker.ietf.org/doc/html/rfc1981) for
IPv6.

The mechanism is fundamentally the same, and so are the problems.

## IPv4

As described in the [IP Fragmentation section](ip_frag.md), when a router is
unable to TX an IPv4 with the DF=1 on a link because of its size exceeding the
MTU:

* Will drop the packet
* _Should_ send and ICMPv4 packet back to the originating host:

```
pkt=IP(src=routerIP, dst=orig_pkt_srcip)/ICMP(type=3, code=4)/<original IP | L4 | up until the first 64 bytes of the pkt>
```

With:
   * Source IP: the router IP
   * Destination IP: original packet source IP (originator)
   * ICMP type=3 (`Destination Unreachable`), code=4 (`Fragmentation required,
     and DF flag set`) with MTU of next hop, which is the maximum MTU that a
     router can use to forward packets to that next hop.
   * The first 64 bytes of the packet as payload. This typically includes the
     L3 and L4 headers, so that PMTUD can work on a per flow basis.

The originator host can then take the information of the ICMP packet received to
adjust the effective MTU. This is known as Path MTU Discovery.

## Why it's broken?

PMTUD has a number of problems:

* Some routers don't generate ICMP packets: see the next section for details.
* Some routers rate limit ICMP: on certain misconfigurations or under certain
  DoS, ICMP rate limits might prevent legitimate traffic to generate the right
  ICMP packets.
* ICMP blackholing: some firewalls block entirely ICMP for security reasons
  (e.g. to avoid forged packets altering PMTUD state).
* NAPTs/Firewall traversal: in non-symmetric NATs, such as [NAPT](https://en.wikipedia.org/wiki/Network_address_translation),
  like IP masquerading, they keep state on a per flow basis to demultiplex
  an incoming packet to the righ internal IP. Unless static mappins are set,
  packets not belonging to a known flow that originated behind the NAT are
  dropped. ICMP packets are packets that are unknown to the NAT, so in order
  to DNAT it to the right internal client, the NAT needs to do ICMP payload
  inspection of the original header. This is not done by all NATs

### Why some routers are not generating ICMP messages, or might be severly rate limited

Besides the obvious - some network operators block entirely ICMP - there are
reasons why ICMP packets might not be generated by routers or be severly rate
limited.

A typical routers handles IP fragmentation in HW, but can't handle ICMP
generation in HW, so they are forced to punt the offending packet from the
forwarding HW to the CPU (so from the line-card to the Supervisor/Routing engine
card via the backplane on chassis routers, or from the HW ASIC to the local CPU
via PCIe or alike on single HW devices).

The backplane / PCIe / etc. has a limited bandwidth, and the control CPU(s)
are also a scarce resource. It is vital to protect the routing stack (routing
protocol traffic that terminates in the router), so that routing is stable and
there are no routing glitches, which can result in route flaps and churn in the
network. MTU exceed IP packets are typically dropped or severly rate limited for
this reason, and the CPU cycles spent for ICMP packet generation also
restricted.

## [Linux] Support for PMTUD

Mind:

* Most of the systems don't modify the default sysctls
* Applications don't usually set the setsockopt of PMTUD for their sockets.

### Default behaviour

By default Linux will:

* Do PMTUD for both TCP and UDP sockets originating in the device. This means
  it will send TCP UDP packets with DF=1, and adjust the effective MTU if
  ICMP packets are received.
* Will NOT do PMTUD for traffic routed through it (it will not modify the DF).

### Controlling PMTUD defaults via sysctl

The following [sysctl](https://docs.kernel.org/networking/ip-sysctl.html) control
the default behaviour for IPv4 (all newly created sockets):

* `ip_no_pmtu_disc`: possible values:
  * `0`: PMTUD is enabled (default)
  * `1`: Disabled, but ICMP needs fragmentation will result in min_pmtu being used.
  * `2`: Like 1, but ICMP messages are ignored.
  * `3`: hardened mode PMTUD (TCP, SCTP only). Verifies seq numbers etc.
* `ip_forward_use_pmtu`: use PMTUD while forwarding (routing) packets. Default
   0 (disabled).
* `min_pmtu`: minimum path MTU value (default: 552). This is essentially to
              avoid fragmenting PMTUD packets themselves.

### Controlling PTMUD on a per socket `setsockopt()`

PMTUD can be controlled on a per socket basis using [setsockopt()](https://man7.org/linux/man-pages/man7/ip.7.html),
`IP_MTU_DISCOVER` parameter with the following options:

 * `IP_PMTUDISC_WANT`: use per-route pmtud settings. With default route
                       configurations this is equivalent to `_DO`
 * `IP_PMTUDISC_DONT`: never do Path MTU Discovery (DF=0).
 * `IP_PMTUDISC_DO`: always do Path MTU Discovery (DF=1), default.
 * `IP_PMTUDISC_PROBE`: set DF but ignore Path MTU.

This is mostly used by network probing tools (e.g. `ping`, `nc` etc.).

### Getting the discovered MTU via `getsockopt()`

You can get the effective discovered MTU via [getsockopt()](https://man7.org/linux/man-pages/man7/ip.7.html)
with the `IP_MTU` parameter.

### PMTUD in action

You can check the [demo](demo/) for seeing how PMTUD discovery works. You must
use the `_nogso` variant:

```
cd demo
make router_nogso
```

The scenario has all veth MTUs set to 1500, except `veth1` that is set to 1400.

You can then test:

* ICMP large packets (technically this is not affected by GSO): `test_large_icmp_request`. 
* TCP large flow: `test_tcp`

You can later use `router_nogso_icmp_blocked` to see how PMTUD is not possible
when ICMP is blocked.
