# Testing PMTUD and PLPMTUD

## Scenario

Simple simulated network with two end-hosts and one intermediate router, using
network namespaces. The topology is [here](scenario.txt).

Note:

* All MTUs set at 1500 bytes by default.
* GSO/TSO/UFO `on` on all interfaces.

Create the scenario using `make` and clean it up with `make clean`.

### Config targets

These targets modify the configuration of the scenario:

* MTU related:
  * `set_link1_default mtus`: restores `link1` mtu to 1500 (matching MTUs)
  * `set_link1_mismatched_mtus`: sets router's (veth1) to 1400, veth0 to 1500
  * `set_link1_matching_mtus`: sets `link1` mtu to 1500 (matching MTUs).
* TSO/GSO/UFO:
  * `{enable|disable}_gso_tso_ufo`: {enables|disables} GSO/TSO/UFO on all interfaces
* Controlling ICMP on the router:
  * `{unblock|block}_icmp`: block or unblock ICMP generated by the router
* MTU probing / PLMPTUD:
  * `{enable|disable}_mtu_probing`: enable or disable MTU probing (TCP PLPMTUD) on
     `host2` namespace.

### Testing targets

* `test_large_icmp_request`: send 3 ICMP requests from `host2` to `host1` with
   1401 bytes of MTU (`-s 1377`). Will dump all packets with tcpdump.
* `test_tcp`: sends a large file via a simple TCP socket (netcat). Will dump
   the 100 first packets (tcpdump)

### Other

* `shell_{host1|router|host2}`: open a shell in the network NS.

### PMTUD: lowering the MTU (symmetrically)

In order to see PMTUD in action, lower the MTU to 1400 on `link1` using
`set_link1_matching_mtus`. Also disable TSO/

When using `test_large_icmp_request`, host2 will send an ICMP request larger than
the 1400 MTU. This packet doesn't exceed `link2`'s MTU but does exceed now
`link1`. Given that the ICMP request is setting the `DF=1`, and `router` is
unable to TX the packet on `veth1`, the `router` will emit an ICMP message
back to `host2`:

```
16:51:19.891153 f6:ae:20:3f:c8:57 > da:54:54:6a:87:c3, ethertype IPv4 (0x0800), length 1419: (tos 0x0, ttl 64, id 12874, offset 0, flags [DF], proto ICMP (1), length 1405)
    192.168.1.2 > 192.168.0.2: ICMP echo request, id 4947, seq 1, length 1385
16:51:19.891172 da:54:54:6a:87:c3 > f6:ae:20:3f:c8:57, ethertype IPv4 (0x0800), length 590: (tos 0xc0, ttl 64, id 12827, offset 0, flags [none], proto ICMP (1), length 576)
    192.168.1.1 > 192.168.1.2: ICMP 192.168.0.2 unreachable - need to frag (mtu 1400), length 556
```

The result is that the first ICMP request will be lost, but the subsequent
ICMP requests will be fragmented in origin, as the "effective MTU" towards
`192.168.0.2` has been lowered to 1400:

```
16:51:20.902899 f6:ae:20:3f:c8:57 > da:54:54:6a:87:c3, ethertype IPv4 (0x0800), length 1410: (tos 0x0, ttl 64, id 13302, offset 0, flags [+], proto ICMP (1), length 1396)
    192.168.1.2 > 192.168.0.2: ICMP echo request, id 4947, seq 2, length 1376
16:51:20.902923 f6:ae:20:3f:c8:57 > da:54:54:6a:87:c3, ethertype IPv4 (0x0800), length 43: (tos 0x0, ttl 64, id 13302, offset 1376, flags [none], proto ICMP (1), length 29)
    192.168.1.2 > 192.168.0.2: ip-proto-1
16:51:20.902933 da:54:54:6a:87:c3 > f6:ae:20:3f:c8:57, ethertype IPv4 (0x0800), length 1410: (tos 0x0, ttl 63, id 11121, offset 0, flags [+], proto ICMP (1), length 1396)
    192.168.0.2 > 192.168.1.2: ICMP echo reply, id 4947, seq 2, length 1376
16:51:20.902933 da:54:54:6a:87:c3 > f6:ae:20:3f:c8:57, ethertype IPv4 (0x0800), length 43: (tos 0x0, ttl 63, id 11121, offset 1376, flags [none], proto ICMP (1), length 29)
    192.168.0.2 > 192.168.1.2: ip-proto-1
```

Note that the second fragment has only the remaining bytes, no L4 (ICMP).

If you now run a second time `test_large_icmp_request` you will see that there
are no ICMP requests lost, and no PMTUD is triggered. This is because the
effective MTU towards `192.168.0.2` is cached (you can clean it up running
`ip route flush cache` in the `host2` NS. 

If you now run `test_tcp` you will see no changes.

### Disabling TSO/GSO/UFO and checking TCP: MSS during 3way handshake in action

Disable TSO/GSO/UFO using `disable_gso_tso_ufo` and retry `test_tcp`. You should
now see that packets are not anymore 16K bytes, but rather within the 1400 bytes
MTU (1414 bytes packets):

```
17:09:34.025769 f6:ae:20:3f:c8:57 > da:54:54:6a:87:c3, ethertype IPv4 (0x0800), length 1414: (tos 0x0, ttl 64, id 52332, offset 0, flags [DF], proto TCP (6), length 1400)
    192.168.1.2.32964 > 192.168.0.2.12345: Flags [.], cksum 0x87bf (incorrect -> 0x5ee2), seq 63981:65329, ack 1, win 502, options [nop,nop,TS val 2615403281 ecr 3831419964], length 1348
```

The rate of transfer should have lowered considerably, as a result of disabling
GSO.

But why is PMTUD not triggered? You can try `flush_cache` target, and retry
the ICMP and TCP tests, and you will see that TCP is never triggering PMTUD.
